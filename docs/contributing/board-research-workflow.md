# ChatMaker 新板卡调研流程

需要标准化流程。原因很简单：板卡名字相似、硬件版本不同、工具链也不同；如果直接复制上一块板的做法，很容易出现“程序能编译，但板子并不是这一款”或“串口有文字，就误以为屏幕已经显示”的问题。

## 开始前的范围卡

每块新板先写三行：

```text
必须改：本轮要增加的精确板卡、代表案例和证据门。
绝不改：不顺带改造的其他板卡、发布设施和未授权模块。
验收证据：至少一个代表案例，以及本轮实际能完成的编译、上传、串口或实体检查。
```

## 八步流程

1. **确认精确型号**：记录正反面名称、硬件版本、芯片和关键外设；名字相似的板卡必须分开。
2. **只收官方一手资料**：优先使用产品页、硬件文档、官方源码、工具链和许可证；社区文章只能作为线索。
3. **建立结构化板卡事实**：把芯片、引脚、电压、板载模块、风险和来源写入板卡记录，未知项保持未知。
4. **确定正式工具链**：核对编译器、核心、库、上传方式、串口方式、版本锁定和分发许可。
5. **选择一个代表案例**：案例应尽量覆盖这块板最有代表性的输入、输出和交互，但不能用一个案例代表所有功能。
6. **分门验证证据**：分别记录环境准备、源码生成、编译、上传、串口、断电重启和实体效果；没有观察到的门不能写成成功。
7. **生成 Knowledge 摘要**：详细事实保留在结构化数据中，Knowledge 与 README 只引用或生成小白摘要。
8. **做最低充分验证**：运行直接覆盖改动的聚焦测试，再走一条代表性 Knowledge 读取路径；发布签名知识包只在本阶段确实需要时进行。

## 每块板的完成记录

```text
板卡：精确型号与硬件版本
官方来源：产品页／硬件文档／源码／许可证
工具链：名称、版本、下载来源、是否需要桌面应用
代表案例：案例名与覆盖功能
证据门：环境／编译／上传／串口／断电重启／实体效果
仍未验证：明确列出
Knowledge：板卡记录、索引、章节和知识包状态
```

## 掌控板和 micro:bit 的安排

- **P2.1 经典掌控板 V2.x**：当前第一优先。仓库已经有板卡记录和 Knowledge，下一步是补独立工具链与实体验证。掌控板 3.0 必须另开精确型号路线。
- **P2.2 micro:bit V2**：当前第二优先。先比较 MakeCode、MicroPython/CODAL 等官方路线，再选择最适合 ChatMaker 的 CLI；不直接复制星核板的 Arduino 方案。micro:bit V1 只有在真实需求出现时再补。
