# Contributing Data and Knowledge Packs

Create one YAML file per record under `packs/boards`, `packs/components`, or `packs/recipes`. Use lowercase hyphenated IDs and keep IDs unique across all record kinds.

Run:

```powershell
python runtime/doctor.py --packs
python -m unittest discover -s tests -v
```

A contribution must cite its sources and preserve all four baseline evidence gates. Set any gate to `verified` only with a date and a specific evidence note. Recipes may add extension gates such as `wifi_ap_available` or `http_exchange_verified`, but only when that recipe actually needs the extra runtime proof. Boards and components should not inherit recipe-only extension gates by default. When a recipe references a board or component, that ID must already exist. Two wires may share a board pin only when every connection explicitly sets `shared: true`; this is intended for reviewed buses or power rails, not accidental signal conflicts.

## Canonical data stays in Core

`packs/boards`, `packs/components`, and `packs/recipes` are the only source of canonical board, component, and recipe facts. The minimal Core contains exactly 3 board files, 12 component files, and 14 recipe files, plus every schema and three compact files under `knowledge/boards`.

Do not copy canonical YAML into a knowledge pack. A silently installed pack containing a board, component, recipe, hook, dependency, script, or executable is invalid.

## Passive ChatMaker Knowledge `.cmpack`

Each optional archive contains detailed pages for exactly one board. Its `pack_id` must be one of the three allowlisted IDs and its payload may contain only:

```text
pack-manifest.json
knowledge/index.yaml
knowledge/sections/<section-id>.md
```

Follow the [ChatMaker Knowledge page format](knowledge-format.md). `pack-manifest.json` is generated by `scripts/build_pack.py`; do not add it to the source tree yourself.

Build from a prepared payload root whose contents are exactly:

```text
<prepared-source-root>/
  knowledge/
    index.yaml
    sections/
      <section-id>.md
```

Copy `knowledge/boards/<board-id>.yaml` to `<prepared-source-root>/knowledge/index.yaml`, then copy the approved published section pages from `knowledge_sources/published/boards/<board-id>/*.md` into `<prepared-source-root>/knowledge/sections/`. Never build from `knowledge_sources/raw` or `knowledge_sources/cleaned`. Do not pass `knowledge_sources/published/boards/<board-id>` directly to `--source`; that directory is missing the required `knowledge/` boundary and will fail with `source_path_not_allowed`.

From repository HEAD, a runnable example for `arduino-nano-classic` is:

```powershell
python scripts/build_pack.py --source <prepared-source-root> --output <output-pack-path> --pack-id chatmaker-board-arduino-nano-classic-knowledge --pack-version 1.0.0 --board-id arduino-nano-classic --core-minimum 0.1.0 --core-maximum-exclusive 0.2.0
```

The builder freezes path spelling, file order, timestamps, permissions, compression, lengths, and SHA-256 values so the same source produces identical bytes. Keep `.cmpack` artifacts under `distribution/packs/`; they are optional downloads and must not enter `ChatMaker-Core-<version>.zip`.

## Registry and signing boundary

An official registry entry records the exact `.cmpack` byte length and SHA-256 and uses a Raw GitHub URL pinned to the 40-character commit that already contains that artifact. Never use `main`, a tag, or a release redirect as the pack URL.

The detached signature covers the exact bytes of `distribution/registry/registry.json`. The private Ed25519 key must stay outside the repository. `scripts/sign_registry.py` fails closed unless the external key exists and its derived public key matches the checked-in trust anchor. Never print, copy, commit, replace, or generate an official private key during release work.

Content installation, update, cache inspection, and rollback are owned only by `chatmaker-pack`. Host installers must not duplicate those actions or edit Codex/WorkBuddy configuration during content updates.
