# ChatMaker Knowledge、通用安装与星核板接入设计

## 目标

本阶段把 ChatMaker 从已经可用的 Nano、Uno、ESP32 创作工具，升级为更容易分发、扩展和维护的创作伙伴：知识层统一命名为 **ChatMaker Knowledge / ChatMaker 知识库**；用户只需一个通用入口即可安装和自检；星核板作为第一块自研硬件正式接入公开知识系统。

这一阶段不实施 ChatCAD、DXF、3D 外壳生成，也不添加资料尚未确认的星辰板。当前没有实体开发板，因此编译、静态检查和知识来源可以验收，烧录、串口和实际硬件效果必须继续标记为未验证。

## 整体架构

```text
用户表达想法
    ↓
ChatMaker 理解需求并推荐方案
    ↓
确认准确的板卡身份
    ↓
ChatMaker Knowledge 读取该板卡资料
    ↓
ChatDuino / ChatWeb 完成作品
    ↓
编译、网页预览或真实硬件验证
```

ChatMaker 是总入口；ChatDuino 负责硬件、接线、代码、编译和烧录；ChatWeb 负责网页、课堂小工具以及网页与硬件交互。三个模块共享同一份板卡知识，不在各自目录复制板卡事实。

知识系统继续使用“规范事实 + 适合 AI 阅读的知识页”两层结构：

- `packs/boards`、`packs/components`、`packs/recipes` 保存可计算的板卡、元器件和案例事实。
- `knowledge/boards` 保存紧凑索引和按需安装的说明页。
- 通用元器件只保存一份，由板卡入口展示兼容关系。
- 所有读取都先确认准确的 board ID；未知板卡不会回退到相似型号。

## 完整改名

当前知识层的旧名称在同一个版本中完成干净改名，不保留兼容别名。用户可见名称为 `ChatMaker Knowledge` 和 `ChatMaker 知识库`，推荐技术名称如下：

```text
CLI          chatmaker-knowledge
MCP tool     knowledge_get
Python       chatmaker.knowledge
目录         knowledge/boards
页面 kind    knowledge-page
索引 kind    knowledge-index
```

运行代码、CLI、MCP、包内路径、schema、错误码、测试、Skills、安装文档和当前架构文档一起迁移。Git 历史保留旧实现的可追溯性，当前工作树和发布物不继续暴露旧名称。

已有 Nano、Uno、ESP32 的稳定 board/component/recipe ID 和事实内容不变。改名改变知识接口的身份，不改变已经验证过的板卡事实。

## 通用自动安装

统一用户入口为：

```text
chatmaker-install auto
```

安装器不先判断用户使用 Codex、WorkBuddy 或某个固定 AI，而是探测当前电脑实际拥有的能力：操作系统、CPU、Python、终端、可写的 Skill 目录、MCP 配置能力、浏览器、串口和已有硬件工具链。宿主差异只存在于内部适配器，用户手册保持一条主流程。

安装顺序如下：

1. 生成只读环境报告，不修改系统。
2. 在用户目录安装最小 ChatMaker Core。
3. 将三个 Skill 安装到当前环境可发现的位置。
4. 在支持 MCP 的宿主中配置共享服务；不支持时保留 CLI 能力。
5. 执行 doctor，返回已完成、未发现和需要用户动作的项目。
6. 第一次使用某块板卡时自动确保对应知识包存在。

安全、可回滚、用户级的变化默认自动完成。只有操作系统要求提权、驱动确认或其他无法静默完成的系统动作时，才向用户说明一个必要步骤。Windows 和 macOS 都进入同一主流程；平台差异由探测器和适配器处理。

当前硬件流程继续优先兼容 Mind+。不安装 Mind+ 的独立编译、烧录和串口环境是下一阶段目标，本阶段只保持清晰接口，不扩大交付范围。

## 按需知识与更新

最小核心只携带运行层、三个 Skill、规范数据、紧凑板卡索引、必要示例和安装说明。详细板卡知识在第一次使用时自动下载。

下载和更新继续遵守现有签名注册表、长度、SHA-256、安全解压、不可变存储、原子激活和回滚机制。改名后的行为保持：

- 下载成功并验证后才激活新版本。
- 更新失败继续使用旧版本。
- 离线时优先读取已经安装的精确版本。
- 离线且从未安装时，明确报告缺少哪个板卡知识包。
- 官方知识包不能覆盖规范板卡、元器件或案例事实。
- 本地覆盖必须显示来源，不能伪装成官方内容。

注册表 sequence 在重新发布知识包时递增。生产签名私钥继续保留在仓库外，构建和测试不得读取、复制或输出私钥内容。

## 星核板知识接入

星核板按独立板卡 `IDMC-0001 星核板 v4.2.2` 处理，建议稳定 ID 为 `idmc-0001-starcore-v4-2-2`。资料管线为：

```text
本地原始资料
    ↓
清洗和结构化
    ↓
来源、版本与冲突复核
    ↓
发布批准
    ↓
公开知识页与签名知识包
```

公开内容包括：板卡识别、安全、电气与引脚使用、Mind+ 软件环境、兼容库、常用模块、示例代码、编译方法和故障排查。原始原理图、Gerber、STEP、完整 DXF、生产文件和其他可直接用于制造的源文件只保留在本地治理目录，不进入 GitHub、Core 或公开知识包。

manifest 记录原始文件标识、哈希、所有权、版本、允许提取的知识范围、清洗状态、来源复核状态和发布批准状态。冲突信息保持待确认，不通过推测生成规范事实。星辰板不创建占位记录；用户提供资料后再走同一流程。

## 错误处理

错误面向普通用户表达为“发生了什么、现在还能做什么、下一步是什么”，程序内部保留稳定错误码用于自动处理。

- 环境能力缺失：报告缺少的能力，不误报安装完成。
- 宿主无法识别：CLI 保持可用，并输出可执行的配置建议。
- 知识下载或验签失败：不激活新包，继续使用旧包。
- 板卡或章节不存在：明确报告精确 ID，不回退到相似板卡。
- 星核板资料冲突：保留未知状态，不发布猜测值。
- 编译失败：保存板卡、工具链、依赖和原始错误，不能升级为已验证。

## 验证与完成标准

### 改名验证

- CLI、MCP、Python、目录、schema、错误码、Skills、测试和当前文档使用新名称。
- 发布包和全局安装的三个 Skill 不再引用旧接口。
- Nano、Uno、ESP32 的既有查询、按需安装、离线读取、更新和回滚回归通过。

### 安装验证

- Windows 在干净临时用户环境中完成 `auto → doctor → knowledge read`。
- macOS 由 GitHub Actions 或等价真实 macOS 运行环境验证同一流程。
- 重复运行安装器是幂等的，不破坏无关 Skill 或 MCP 配置。
- 卸载或恢复路径经过测试。

### 星核板验证

- 公开文件不包含制造源文件。
- 关键板卡事实有可追溯来源和明确证据状态。
- 选定的代表性示例完成实际编译验证。
- 烧录、串口、断电重启和物理效果保持 `unverified`，直到获得实体板复测。

### 发布验证

- 全部自动化测试通过，知识包可重复构建且哈希一致。
- 全局 `chatmaker`、`chatduino`、`chatweb` 与仓库源码一致。
- 推送后确认 GitHub `main` 等于本地已测试提交。
- 从公开 GitHub 注册表完成一次真实按需安装和读取。

## 明确不做

- 不实现 ChatCAD、Chat 2D、Chat 3D、DXF、STL 或外壳生成。
- 不添加星辰板，也不使用星核板资料替代它。
- 不声称完成任何没有实物证据的烧录或物理效果。
- 不在本阶段替换 Mind+ 为完整独立硬件工具链。
- 不创建面向特定 AI 宿主的用户主流程。
